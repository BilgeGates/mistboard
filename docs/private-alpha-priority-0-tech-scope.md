# Private Alpha Priority 0 Tech Scope

Priority 0 work is the safety and continuity gate for wider private-alpha play.
The goal is not to finish every alpha feature. The goal is to make live Fog of
War rooms hard to leak, hard to strand, and easy to verify before inviting more
testers.

## Track 1: Live Privacy / Access Policy

Status: mostly covered by the current policy direction.

Builder readiness: ready to pick up now.

Covered:

- Live PvP replay APIs reject full event access before terminal state.
- Live PvP non-seat spectators are rejected on WebSocket connect.
- PvE and EvE observation policy is separated from PvP.
- Live Fog snapshots and replay APIs redact move events according to mode.

Technical scope:

- Keep PvP, PvE, and EvE mode detection centralized in server policy code.
- Keep spectator gating before any room snapshot is sent.
- Keep public replay APIs aligned with live WebSocket snapshot redaction.
- Keep admin-debug truth access separate from room id, query params, and normal spectator status.

Verification:

- Unit tests for replay API policy and snapshot payload redaction.
- Manual PvP smoke: third live tab is rejected before terminal state.
- Manual PvE smoke: observer sees the human perspective, not engine-only truth.
- Manual EvE smoke: observer sees full truth by design.

Builder-sized next task:

- Add WebSocket-level tests or smoke tooling that proves PvP third-client
  rejection happens before any snapshot, PvE observers receive only the human
  perspective, and EvE observers receive full truth by design.
- Confirm replay API and WebSocket snapshot policy stay aligned.

## Track 2: Reconnect / Session Continuity

Status: partially covered. Basic same-browser refresh recovery works only
because the browser reuses a `clientId` from local storage. That is convenient
but not a sufficient authority model.

Builder readiness: ready to pick up now. The duplicate-tab behavior decision is
locked as newest valid socket wins.

Current model:

```text
clientId in localStorage == seat identity
```

Target model:

```text
clientId == browser/session label
seatToken == authority to act as White or Black
```

### Invariants

- A socket retry must not create an extra seat.
- A browser refresh with valid seat authority should recover the same seat.
- A lost or cleared browser identity must not silently become the other open seat in an active private game.
- A guessed or copied `clientId` must not be enough to reclaim a seat.
- A duplicate tab must have deterministic behavior that is visible to the user.
- A rejected live PvP observer must not receive any snapshot before rejection.

### Proposed Data Model

Keep `clientId` as a non-secret browser/session label:

- generated by the browser
- stored in local storage
- useful for display, logging, and reconnect continuity
- not sufficient for move authority

Add `seatToken` as a secret bearer credential:

- generated by the server when a seat is assigned
- scoped to one room and one color
- returned only to the seated client
- stored by the browser locally with the room id
- sent on future WebSocket connections for that room
- never included in spectator payloads, replay APIs, logs, or public docs examples

Minimum token state:

```text
roomId
seat
tokenHash
issuedAt
lastSeenAt
revokedAt
```

For in-memory development, this can live in the room projection side state. For
durable production-like rooms, it should be persisted as room/session metadata
without exposing the raw token after issuance.

### Server Scope

- Add a seat-token issuance path when a client is assigned White or Black.
- Store only a hash of the seat token server-side.
- Accept reconnect claims as `(roomId, clientId, seat, seatToken)`.
- Validate the token before restoring a seat or accepting moves for that seat.
- Keep existing `clientId` matching as a compatibility aid only, not authority.
- Do not assign an open seat in an already-started private Fog game unless the connection is an authorized reconnect or an explicit new join before play begins.
- Decide duplicate-tab behavior:
  - either allow multiple sockets for the same valid seat token as the same seat, or
  - make the newest valid socket active and mark older sockets read-only/disconnected.
- Return a clear close reason or error payload for missing/invalid seat authority.

Locked duplicate-tab decision:

- Newest valid socket wins.
- Older sockets for the same room/seat token should become read-only or be
  disconnected with a clear reason.
- Rationale: this avoids double-input ambiguity, is easier for testers to
  understand, and keeps the model compatible with future account/session
  behavior.

### Client Scope

- Store room-scoped seat tokens separately from the generic `clientId`.
- Send the seat token on reconnect for the matching room.
- Preserve current socket retry/backoff behavior.
- Show reconnect, rejected, and duplicate-session states distinctly.
- If local storage is missing or cleared, treat the user as unauthenticated for that seat instead of guessing.
- Avoid putting tokens in URLs.

### Compatibility / Rollout

Implement in small slices:

1. Add server-side token issuance and return it in the seated `hello` payload.
2. Store and resend the token from the web client.
3. Require valid seat tokens for reclaiming occupied seats and for move authority.
4. Add duplicate-tab semantics.
5. Remove or downgrade legacy `clientId`-only seat reclaim after a short compatibility window.

Builder-sized implementation slices:

1. Server token issuance: generate a seat token on assignment, store only a
   hash, and return the raw token only in the seated `hello` payload.
2. Client token storage: store room-scoped seat tokens, resend them on
   reconnect, and never put tokens in URLs.
3. Authority enforcement: require a valid seat token to reclaim an occupied
   seat and to move as that seat; keep `clientId` as a label only.
4. Duplicate-tab semantics: implement the locked behavior and expose a clear UI
   state for displaced or read-only tabs.
5. Regression tests: cover valid reclaim, missing/wrong token rejection, copied
   `clientId` without token, and cleared local storage midgame.

### Tests

Server tests:

- valid seat token reclaims the same seat
- missing token cannot reclaim an occupied seat
- wrong token cannot reclaim an occupied seat
- copied `clientId` without token cannot move
- live PvP overflow connection is rejected before snapshot
- active private game does not auto-seat a new unknown client into an abandoned color

Browser/manual smoke:

- refresh White tab and recover White
- refresh Black tab and recover Black
- close socket and recover via retry
- duplicate White tab behavior is deterministic
- clear local storage midgame and confirm the user does not regain move authority
- complete game and confirm postgame review still works

## Track 3: QA / Release Readiness

Status: scoped, but the manual gate needs to be made explicit and repeatable.

Builder readiness: ready to pick up now.

Technical scope:

- Split the public QA checklist into a short private-alpha smoke path and broader exploratory checks.
- Include PvP, PvE, EvE, reconnect, duplicate-tab, and postgame review coverage.
- Record found bugs as expected/actual behavior with room URL, move sequence, and browser context.
- Convert privacy, reconnect, rules, or persistence bugs into regression tests when feasible.
- Keep provider-specific deploy and incident steps out of public docs.

Verification:

- One production-like build completes the private-alpha smoke path.
- Known limitations are either fixed or documented in public-safe terms.
- Unit tests and smoke checks are enough for a future session to repeat without rediscovering the plan.

  broader exploratory checklist.
