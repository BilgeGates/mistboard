# Identity And Profiles

This document defines Bichess identity concepts before they become platform
features. It is a product and technical scope note, not an implementation plan.

Identity work should support Fog of War play, replay, engine development,
research artifacts, and transparency without pulling ratings, matchmaking, or
social-network features into v1.

## Core Distinction

Bichess should keep these concepts separate:

- display identity: what a user or artifact is called
- authority: what permits an action
- ownership: what persists across sessions
- public profile: what other people can inspect

Do not use one identifier for all four jobs.

## Current Identities

### Anonymous Browser Session

Purpose: represent a browser/session during anonymous play.

Current shape:

- `clientId`
- generated client-side or server-side
- stored locally by the browser
- useful for reconnect continuity, logging, and room display

Important limit:

- `clientId` is not a secret
- `clientId` should not be enough to reclaim a seat or make moves

Target posture:

```text
clientId == browser/session label
seatToken == authority to act as White or Black
```

### Room Seat

Purpose: represent White or Black in a specific room.

Authority should come from a room-scoped seat credential, not from display
identity.

Target authority:

- `seatToken`
- scoped to room id and color
- generated by the server
- stored by the browser locally
- sent on reconnect
- never placed in URLs, replay APIs, logs, or spectator payloads

Public display:

- "White"
- "Black"
- optional guest label later

### Engine Identity

Purpose: identify a server-side or research engine that plays games.

Current examples:

- `random-engine`
- `engine:white`
- `engine:black`
- `builtin-*`
- `python-*`

Target posture:

- engine ids should be stable enough for game records and benchmark reports
- engine versions should be distinct from engine families
- engine identity should include enough metadata to interpret results

## Coming Identities

### Signed-In Player

Purpose: let a person persist activity and artifacts across sessions.

Owns or links to:

- games
- room history
- public replays
- annotations
- preferences
- future profile page

Not automatically included:

- ratings
- matchmaking pools
- social graph
- chat

### Engine Author

Purpose: identify a person or group responsible for an engine submission or
published benchmark artifact.

Owns or links to:

- engine families
- engine versions
- benchmark reports
- reproducibility notes
- public limitations or changelogs

### Engine Version

Purpose: identify the exact playable engine used in a game or benchmark.

Owns or links to:

- engine family
- author
- version id
- config hash
- play signature
- allowed observation policy
- benchmark games
- known limitations

Engine version identity matters because benchmark claims are not meaningful
without a reproducible playable identity.

### Contributor / Researcher

Purpose: attribute research artifacts that are not simply player games.

Owns or links to:

- corpora
- annotations
- experiment configs
- benchmark writeups
- review queue contributions

## Ownership Matrix

| Artifact | Guest session | Signed-in player | Engine author | Engine version | Contributor/researcher |
|---|---:|---:|---:|---:|---:|
| Live room seat | yes, via seat token | yes, via seat token/account link | no | no | no |
| Finished game | maybe | yes | maybe, for engine games | yes, for engine games | maybe |
| Public replay | maybe | yes | maybe | yes, for engine games | maybe |
| Annotation | local/temporary | yes | maybe | no | yes |
| Engine family | no | maybe | yes | no | maybe |
| Engine version | no | maybe | yes | yes | maybe |
| Benchmark report | no | maybe | yes | yes | yes |
| Corpus/manifest | no | maybe | maybe | maybe | yes |

## Public Vs Private

Public by default only when intentionally published:

- finished public games
- public engine ids and versions
- benchmark metadata
- public annotations or reports
- contributor names on public artifacts

Private or scoped:

- live PvP player views before terminal state
- seat tokens
- raw session identifiers
- private room links before sharing
- non-public annotations
- operational metadata

Never public:

- raw seat tokens
- secret-bearing environment values
- credentials
- admin-debug tokens
- private provider configuration

## Profile Surfaces

Profiles are deferred as broad social features, but profile primitives matter.

Future profile types:

- human player profile
- engine author profile
- engine version profile
- contributor/research profile

### Human Player Profile

Useful when signed-in persistence exists.

May show:

- public games
- public replays
- annotations the player chose to publish
- profile name
- contribution links

Deferred:

- ratings
- matchmaking history
- teams/forums/chat
- social graph

### Engine Author Profile

Useful for engine development and research credibility.

May show:

- engine families
- submitted versions
- benchmark reports
- reproducibility notes
- public changelogs

### Engine Version Profile

Useful for understanding benchmark and EvE games.

May show:

- version id
- author
- config hash
- play signature
- allowed observation policy
- game corpus
- benchmark record
- known limitations

### Contributor / Research Profile

Useful for attribution of research artifacts.

May show:

- corpora
- annotations
- experiments
- public reports
- review contributions

## Authority Rules

Identity should not imply authority unless an explicit credential or account
session grants it.

Rules:

- `clientId` labels a browser/session; it does not authorize play.
- `seatToken` authorizes a room seat.
- account session authorizes persistent user actions.
- engine credentials or registry controls authorize engine submission.
- public profile identity does not authorize private room access.

## Stage Guidance

Stage 1: Private Alpha

- keep anonymous rooms
- use seat tokens for live authority
- avoid public profiles
- preserve finished game ownership metadata when available

Stage 2: Public Alpha

- introduce guest/signed-in persistence only where it improves recovery,
  replay ownership, or artifact management
- keep ratings and social features deferred
- publish clear privacy and replay rules

Stage 3: Research / Engine Alpha

- make engine identities and versions first-class
- publish reproducible benchmark metadata
- support author/contributor attribution

Stage 4: Early Platform

- add profile pages only when they serve real player, engine, or research
  workflows
- revisit ratings, social graph, and community features only after moderation
  and fairness obligations are understood

## Open Questions

- What is the minimum signed-in account model needed for persistence without
  pulling in social features?
- Should engine authors be normal user accounts with extra engine ownership, or
  a separate identity type?
- How should guest games be claimed by a later signed-in account?
- Which annotations are private, shared-by-link, or public?
- What profile fields are required for benchmark credibility without creating
  unnecessary social surface area?
